## שינוי הסכימה המדויק המבוקש

אין טבלאות חדשות ואין עמודות חדשות ב־`documents`.

| טבלה | שינוי |
| --- | --- |
| `billing_attempt` | `operation ENUM('CHARGE','REFUND') NOT NULL DEFAULT 'CHARGE'` |
| `billing_attempt` | `source_payment_event_id INT NULL`, FK ל־`billing_event.id`, מחיקה RESTRICT ועדכון CASCADE |
| `billing_attempt` | `request_id VARCHAR(36) ... COLLATE utf8mb4_bin NULL`, אינדקס UNIQUE |
| `billing_attempt` | `requested_by_firebase_id VARCHAR(255) NULL`, `refund_reason VARCHAR(500) NULL` |
| `billing_attempt` | `refund_provider_transaction_id VARCHAR(128)` מחושב STORED: מספר קארדקום כאשר `operation='REFUND'`, אחרת NULL |
| `billing_attempt` | `obligation_id` ו־`plan_id` נעשים nullable כדי לייצג זיכוי ללא חוב חדש |
| `billing_attempt` | הוספת `REFUND` ל־`trigger` ו־`TRANSACTION_REFUND` ל־`charge_mode` בסוף ה־ENUM, ללא הסרת ערכים קיימים |
| `billing_attempt` | אינדקס source על `(source_payment_event_id,operation,status)` ואינדקס recovery על `(operation,status,next_action_at)` |
| `billing_attempt` | UNIQUE על `(provider_terminal_ref,refund_provider_transaction_id)` |
| `billing_event` | הוספת `REFUND_REQUESTED`, `REFUND_SUCCESS`, `REFUND_FAILED`, `REFUND_RESOLUTION` בסוף ה־ENUM, תוך שמירת סדר וערכים קיימים |
| `billing_event` | `refund_success_attempt_id INT` מחושב VIRTUAL כאשר סוג האירוע `REFUND_SUCCESS`, עם UNIQUE |
| שתי הטבלאות | ארבעה טריגרי BEFORE INSERT/UPDATE לאכיפת סוג הפעולה וסכומי אירוע הזיכוי |

הטריגרים משאירים דרישת חוב ותוכנית לחיוב רגיל, ומחייבים מקור, UUID, מנהל,
סיבה, מסוף, סכום חיובי וסוגי trigger/mode מתאימים לזיכוי. אירוע הצלחה של זיכוי
חייב להיות מקושר לניסיון ולכלול סכומים שליליים שסכומם מתאים. אילוצי הסכומים,
מפתחות החיובים ו־UNIQUE של `documents.billing_attempt_id` נשארים כפי שהם.
נעשה שימוש בטריגרים משום ש־MySQL 8 אינו מאפשר את ה־CHECK הנדרש על עמודות עם
FK cascading. הסכום בניסיון נשאר חיובי; הסכום באירוע ההיסטוריה שלילי.

## קבצי SQL וסדר הרצה

1. [בדיקות מקדימות, קריאה בלבד](../../backend/scripts/migrations/2026-10-22_admin_refunds_preflight.sql).
2. [DDL ושער אישור](../../backend/scripts/migrations/2026-10-22_admin_refunds_apply.sql).
3. [בדיקות לאחר השינוי, קריאה בלבד](../../backend/scripts/migrations/2026-10-22_admin_refunds_verify.sql).

הקבצים מכוונים במפורש ל־`keepintax-prod`. **אין להריץ אותם בדב ואין להריץ
את כל `docs/redesign/cutover.sql`.** סקריפט הדב הקיים נשאר מוגבל ל־`keepintax-dev`.
הקובץ המצטבר מכיל רק הפניה לחבילה לאישור; אינו מפעיל את ה־DDL.

קובץ apply הוא **חד־פעמי**, לא runner אוטומטי ולא idempotent. הוא מסרב לסכימה
שכבר כוללת אפילו חלק מעמודות הזיכויים. יש להשוות את פלט ה־preflight לבסיס
הקנוני הקיים, לעצור אם יש הבדל ולתקן את החבילה לפני אישור. בפרט נדרשים MySQL
8.0, טבלאות InnoDB, עמודות INT תואמות, ENUM ללא ברירת מחדל, קישור מסמך ייחודי
לניסיון ונתוני חיובים קיימים תקינים. הרצה ב־MySQL 8.4 או MariaDB דורשת בדיקה חדשה.

נדרשות הרשאות ALTER, INDEX, REFERENCES, TRIGGER, CREATE ROUTINE ו־ALTER ROUTINE
למפעיל, בנוסף לקריאת מידע הסכימה. יצירת טריגרים עשויה לדרוש הרשאת ניהול נוספת
בהתאם להגדרות שרת/בינלוג; יש לבדוק זאת לפני תחילת חלון התחזוקה. אין להרחיב
הרשאות לחשבון האפליקציה כדי להריץ את השינוי.

שער האישור בקובץ apply הוא `PENDING_OWNER_APPROVAL`. רק אחרי אישור מפורש
מחליפים אותו בעותק שנבדק ל־`APPROVED_ADMIN_REFUNDS_2026_10_22`.
החסם אינו תחליף ללקוח SQL שעוצר בשגיאה. השתמשו בלקוח שתומך ב־`DELIMITER`
ובפקודות CREATE PROCEDURE/TRIGGER; בייבוא phpMyAdmin יש לוודא עצירה בשגיאה.
אין להשתמש ב־`--force` או באפשרות להמשיך אחרי שגיאה.

## הגדרות והרשאות לפני הפריסה

יש לבדוק דרך מנגנון ניהול הסודות הקיים, ללא הדפסת ערכים:

- `CARDCOM_API_NAME`, `CARDCOM_API_PASSWORD`, `CARDCOM_TERMINAL_NUMBER` שייכים
  לחשבון ולמסוף הפרודקשן. המפתח מורשה לביטול עסקה במסוף החיוב המקורי.
  ההרשאות שתוקנו בטסטים אינן מוכיחות הרשאות פרודקשן.
- `COMPANY_BILLING_FIREBASE_ID` ו־`COMPANY_BILLING_BUSINESS_NUMBER` מזהים את
  העסק המנפיק הקיים; אין להחליפם בפרטי הדב. מסמך המקור חייב להתאים לעסק הזה.
- `FILLFASTER_API_TOKEN` קיים; החתימה היא אותה חתימה של מסמכי החיוב הקיימים.
- Firebase Storage: `FIREBASE_STORAGE_BUCKET` והרשאות הזהות של הבקאנד תקינים.
- `BREVO_API_KEY`, `BREVO_SENDER` תקינים, כולל הרשאת שליחה/כתובת שולח מאומתת.
- ב־Cloud Run: `PDF_SERVICE_URL` וההרשאה של זהות הבקאנד לשירות ה־PDF הפרטי
  נשארים פעילים. אין להחזיר PDF לא חתום כפתרון לכשל.
- `NODE_ENV=production`, מומלץ גם `DISABLE_SYNCHRONIZE=true` ו־`SKIP_BOOT_SEED=true`
  לחלון זה; אין להפעיל synchronize כדי ליישם את הסכימה.
- Frontend נבנה ב־production configuration ומצביע ל־API הנכון.
  Checkout/webhook URLs הקיימים נשארים לפי הגדרות הפרודקשן. זיכוי עצמו מקבל
  תשובה ישירה ואינו תלוי ב־ngrok או בהמתנה ל־webhook.

## חלון פריסה לאחר אישור

1. לרענן שוב origin/main לפני המיזוג העתידי. אם השתנה אחרי הבסיס הרשום,
   לעדכן את הענף ולבדוק שוב. מיזוג, push ופריסה עדיין טעונים אישור המשתמש.
2. להכין ולזהות ארטיפקטים של backend/frontend מאותו commit, ולשמור את הגרסה
   הקודמת. לא להפעיל revision חדש לפני הכנת הסכימה.
3. להריץ preflight באמצעות המפעיל המורשה. לשמור פלט סכימה וספירות מצומצם
   לאישור; אין צורך במידע לקוחות או סודות. לוודא שכל תנאי הבסיס מתאימים.
4. לבחור זמן שקט, לחסום תחילת checkout/פעולות מנהל חדשות ולהשלים תשלומים
   בתהליך. לעצור **כל** הכותבים: כל מופעי backend, cron, workers וכלי מנהל.
   אין להשאיר revision ישן שמבצע כתיבות במקביל. לתכנן קליטת callbacks בזמן
   התחזוקה לפי המנגנון הקיים; אין להניח שספק ישלח שוב webhook שאבד.
5. לקחת גיבוי/נקודת שחזור עדכניים ולוודא אפשרות שחזור. להריץ שוב preflight
   לאחר עצירת הכותבים ולרשום ספירות attempts/events/documents/debt_links.
6. לאחר אישור הקובץ הסופי, להריץ apply פעם אחת, באותו חיבור SQL עד הסיום.
   lock_wait_timeout מוגבל ל־30 שניות. DDL עלול לבנות טבלה מחדש; אין הבטחת
   online/instant או משך ריצה קבוע. **כל שגיאה עוצרת את הפריסה.**
7. לבדוק שכל ארבע השוואות הספירות בסוף apply הן `1`. להריץ verify ולוודא:
   10 עמודות attempt נבדקות; 2 עמודות event; 5 אינדקסים חדשים (10 שורות
   index-column); FK מקור נכון; 4 טריגרים עם גוף תואם; אילוצים קיימים נשמרו;
   ספירות unchanged וכל invalid count אפס. בשלב זה כל הניסיונות הישנים CHARGE.
8. להפעיל את גרסת הבקאנד החדשה עם synchronize כבוי; לבדוק בריאות/לוגי startup
   ושאין שגיאת עמודה/ENUM/trigger. לאחר מכן להעלות frontend מאותה גרסה.
9. לפתוח תנועה בהדרגה ולבדוק שמסכי תשלום קיימים, מנויים והיסטוריה נטענים.
   בדיקת עשן אינה יוצרת חיוב או זיכוי כספי.
10. זיכוי אמת ראשון יבוצע רק ביוזמת מפעיל מורשה וללקוח שבאמת נדרש לו החזר.
    לא ליצור עסקת ניסוי כספית בפרודקשן. לאמת קוד 0 ומספר זיכוי, מסמך יחיד,
    PDF חתום, אימייל, שורת מינוס להורדה ומנוי ללא שינוי.

## שחזור, ניטור וחזרה לאחור

- אם ה־DDL נכשל: להשאיר את הכותבים עצורים ולשמור את השגיאה ופלט הסכימה.
  MySQL מבצע commit ב־DDL; `ROLLBACK` לא מחזיר עמודות/אינדקסים/ENUM. אין להריץ
  את הקובץ מחדש עיוור. routine זמני עשוי להישאר אם CALL נכשל; מסירים אותו רק
  אחרי בדיקת המצב ותוכנית המשך מאושרת. עדיפה השלמת השינוי קדימה לפי המצב בפועל.
- לפני שנוצר ניסיון REFUND כלשהו, אפשר לשקול חזרה לגרסת הקוד הקודמת אחרי
  בדיקה שאין רשומות REFUND, תוך השארת ההרחבה בסכימה. יש לתעד ולאמת זאת.
- **אחרי יצירת REFUND אין להחזיר backend ישן שאינו מבחין בין CHARGE ל־REFUND.**
  לעצור פעולות חדשות, לשמור את רשומות הזיכוי ולתקן קדימה או לבחור גרסה תואמת.
  אין למחוק מסמכים, ניסיונות, אירועים או טריגרים כדי להסתיר תקלה.
- שחזור גיבוי אחרי כסף שנשלח עלול לאבד ראיות לזיכוי ולגרום לכפל החזר.
  נדרש תהליך התאמה לקארדקום; לא לבצע restore אוטומטי או retry כספי.
- UNKNOWN/MANUAL_REVIEW דורש בירור ותיעוד סופי; recovery לא שולח זיכוי נוסף.
  CAPTURED עם מסמך/אימייל ממתינים ניתן להשלים מהפופאפ ללא החזר כספי נוסף.
- לנטר `REFUND_RESULT_UNCONFIRMED`, `REFUND_DOCUMENT_PENDING`, הודעות
  `Refund ... completion failed at ...` ו־`Refund recovery unavailable`.
  בפופאפ מוצגים שלב, הודעה מסוננת ושעה. cron כל דקה משלים מסמכים עם backoff.
- זיכוי שנעשה מחוץ לאפליקציה אינו מסתנכרן אוטומטית ליתרה המקומית. יש לברר
  ולתאם את הרישום; כפתור הבדיקה מול הספק אוסף ראיות ואינו מתקן יתרות בעצמו.
- קודים לא־אפס, כולל 671/5122, נשארים לבירור שמרני. אין כיום סיווג אוטומטי
  של הקודים האלה לדחייה סופית. מנהל מתעד את הכרעתו אחרי אימות מול הספק.
- אימייל יכול להישלח שוב אם ספק המייל קיבל אותו והתהליך נפל לפני שמירת הדגל;
  זה אינו יוצר זיכוי כספי או מסמך נוסף.

## ראיות בדיקה וגבולות האישור

תוצאות הבדיקות המשולבות וה־commit הסופי יתועדו בקובץ
[המשימה](../tasks/active/admin-refunds.md).
הסכימה הלוגית כבר הוכנה ונבדקה בדב עם טריגרים ו־UNIQUE/FK. אין בכך אישור
לסכימת פרודקשן שלא נקראה, וה־SQL החד־פעמי החדש אינו נחשב למורץ רק משום
שהדלתא המקבילה עברה בדב. יש לאמת preflight ולבצע rehearsal בסכימת בדיקות
מבודדת תואמת לפני ביצוע בפרודקשן. לא בוצעו כאן גישה לפרודקשן או ניסוי כספי.
