# PDF startup warmup - 2026-11-25

## Implemented behavior

Standalone production/local entrypoints now perform one synthetic, unsigned PDF render before binding their listener or announcing readiness. This warms the existing single cached Chromium, fonts, layout and PDF-print path. The generated bytes are discarded; the context is closed. Every customer request continues to get a fresh isolated BrowserContext; concurrency one, network/script blocks, deadlines, cleanup, browser recycling after 100 uses and fail-closed rendering remain intact. No user/page/model cache is introduced.

Startup fails and closes the renderer if warmup fails; it never publishes a ready listener first. PDF_WARMUP=false explicitly disables this startup step for operator rollback. No background render competes with an accepted request. Startup logging contains warmup flag and elapsed startupMs only, plus existing service metadata. Existing development render-stage diagnostics were split into CONTEXT_CREATE, PAGE_CREATE and PAGE_SECURITY to expose preparation overhead without content logging. Other stages are unchanged.

Warmup shifts work before readiness; it is not free. A platform that starts an instance because a customer request arrived will still make that request wait for startup/warmup. To hide this work from a user, an already-ready instance must exist before the request. No cloud minimum-instance, billing, probe, runtime or deployment configuration was changed. Browser crashes/recycling can still cause later cold launches; no steady latency guarantee is claimed. Local backend fallback rendering without PDF_SERVICE_URL is unchanged.

## Diagnostic comparison

Baseline product commit 54cb0da4, exact renderer source privately preserved before edits. Benchmark uses fresh actual local Chrome per repetition, original/copy pairs for short document, deterministic 512x512 raster-logo document and 55-row document containing a synthetic allocation marker. No application, DB, signing credentials, mail or storage was used. Allocation marker does not represent a real Tax Authority call. Each table cell contains two measured pair times, in seconds.

| Scenario | Repeated baseline, no warmup | Final code, warmup completed |
| --- | ---: | ---: |
| short | 1.494 / 1.324 | 0.588 / 0.533 |
| logo | 1.101 / 1.087 | 0.846 / 0.786 |
| allocated-multipage | 1.331 / 1.242 | 0.951 / 0.977 |

Final warmup itself took 0.714s / 0.645s. Thus the first short pair after readiness took 0.588s / 0.533s, but warmup plus that pair totals 1.302s / 1.178s, compared with repeated baseline 1.494s / 1.324s. The main proven behavior is preparation before readiness, not elimination of all cold-start work.

Five bounded diagnostic batches ran: initial baseline, experimental warmed candidate, experimental candidate without warmup, repeated baseline and final warmed code. Each batch rendered 12 PDFs (60 PDFs total, plus four synthetic warmup PDFs across warmed batches). An experimental parallelization of independent page-security setup calls did not produce consistent gains and was removed. The first candidate and no-warmup candidate are mixed-revision evidence, not final-source verification. Final warmed batch, final tests and final HTTP/layout smoke used the consolidated source. Timings vary between runs; the logo/multipage differences do not prove a stable warm steady-state gain. These short synthetic times cannot replace the previous full DEV times or establish an overall issuance SLA.

Sanitized raw stage data, source hashes and batch identity are in [evidence](evidence/pdf-startup-2026-11-25.json). Private synthetic PDFs and baseline source are in ignored .test-tmp/pdf-startup. Benchmark includes file-write time in pair totals; per-file elapsedMs measures rendering only. No thresholds were weakened to get a performance pass.
